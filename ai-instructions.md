## ELK Garden — implementation defaults

When changing **frontend UI** in this repo:

- **Tailwind-first**, **minimal custom CSS** — see `docs/elk-garden/style-guide.md`.
- **Reuse shared components** for cards, section headers, and repeated layouts; avoid one-off page styling.
- **Keep primary tabs visually consistent** (Dashboard, Plan, Tasks): same typography hierarchy and spacing rhythm unless the task explicitly says otherwise.
- **Think product, not prototype** — scalable, maintainable, trustworthy surfaces.

Best way to use me during builds

You’ll get the most from me if you ask in one of these modes:

Product mode
	•	“What should this page really do?”
	•	“What’s missing?”
	•	“What order should I build this in?”

Prompt mode
	•	“Write the Cursor prompt”

QA mode
	•	“Here are screenshots, what’s wrong?”
	•	“What should I test?”

Cleanup mode
	•	“We moved fast and got messy, help me stabilize”

New Product Planning Template

1. Product idea
What is the idea in one sentence?

2. Real problem
What real problem does this solve?
What frustration, cost, confusion, or missed opportunity exists today?

3. User
Who is this for?
Who is the first real user?
Would I use it myself right now?

4. Core job
What is the product helping the user do?
Finish this sentence:
“This helps someone ________.”

5. Why this instead of something else?
Why not just use:
- ChatGPT
- Notes app
- Spreadsheet
- Google search
- existing apps

6. Product shape
What kind of thing is this?
- dashboard
- planner
- tracker
- advisor
- checklist
- marketplace
- workflow tool
- content system
- service business
- something else

7. V1 promise
What is the smallest useful version?
What should a user be able to do in version 1?

8. Not now
What features are explicitly out of scope for now?

9. Inputs
What information does the system need from the user?

10. Outputs
What useful thing does the system produce?

11. Memory
Should this product remember anything over time?
If yes, what matters most?

12. Success criteria
How do we know this is useful?
What would make us say “this is working”?

13. Build order
What should be built first?
What should be second?
What should be left for later?

14. Risk check
What could make this fail?
- no real need
- too broad
- too hard technically
- poor UX
- weak differentiation
- legal / trust problems
